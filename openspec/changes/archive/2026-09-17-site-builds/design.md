# Design
**One artifact, rebuilt whole.** GitHub Pages serves a single artifact per deployment, so a preview cannot be added beside a site that is already up: every run builds everything from `main` and the pull requests open at that moment (`gh pr list`), which also makes closing a pull request the way its preview leaves. `scripts/build-pages.mjs` does the work with Node's standard library and git: `git archive` of `main` into the output, then for each pull request `git fetch origin +refs/pull/N/head`, `git archive` into `pr/N/`, the preview changes, and last `builds/index.html`, `builds/builds.json` and `.nojekyll`. Development files (`test`, `openspec`, `scripts`, `node_modules`, `.github`, `.claude`, `package-lock.json`) are left out of every tree. Runs are serialised by a concurrency group without cancelling a deployment in progress; a run that is waiting is replaced by a newer one, which is complete by construction.

**The live app stays at the root.** Moving it would break the installed PWA's scope, bookmarks and shared `#song=` links. The listing is a page beside it, and the app's footer links there. The build adds one tag to the live `index.html`, `<meta name="tutti-builds" content="builds/" data-previews="N">`, and `src/main.js` turns it into the footer link. A marker rather than a request for `builds/builds.json`: the repository's own page has none, so the app asks for nothing, and logs no 404, when it runs locally, in tests or inside a preview.

**`pull_request_target`, and nothing from a pull request runs.** The `github-pages` environment only accepts deployments from `main`, and a `pull_request` run has the pull request's ref, so it could not deploy. `pull_request_target` runs the workflow file and the build script as they are on `main`, with `main` as its ref. That event is dangerous when it checks out and runs a pull request's code with the base repository's token; here the pull request's files are only ever copied (`git archive` to tar to the output directory, no shell, no install, no build step, which the app does not have anyway). Permissions are `contents: read`, `pull-requests: read`, `pages: write`, `id-token: write`. Titles and descriptions are untrusted text: the listing escapes them, links only `http(s)` URLs, and the pull request data handed to the preview's inline script is JSON with `<`, `>`, `&` and the line separators escaped so it cannot close the script.

**Same origin, so previews are fenced.** `ajturner.github.io/tutti-music/pr/7/` shares localStorage, caches and service worker scope rules with the live app. The build prepends a small inline script to a preview's `index.html`, before any module runs, that: prefixes every `localStorage` key with `pr<N>:` by wrapping `Storage.prototype.getItem/setItem/removeItem` for `localStorage` only; makes `navigator.serviceWorker.register` reject, and replaces the preview's `sw.js` with one that unregisters itself and touches no cache, so a preview is never served stale and never competes with the live shell cache; adds the bar, the title prefix and `noindex`. The fence protects the user's songs from an honest preview of a different format (format 4 refuses format 3 autosaves and would otherwise overwrite them); it is not a sandbox, which is why forks get no preview. A branch of this repository is pushed by someone who can already push to `main`.

**The live service worker steps aside.** Its scope is the site root, so it also controls `pr/<n>/` and `builds/`. Left alone it would copy every preview file into the live shell cache and serve a preview's own samples cache-first, which is wrong the moment a pull request replaces a sample in a later push. The fetch handler returns early for paths that, relative to its scope, start with `pr/` or `builds/`. Requests a preview redirects to the live `banks/` are outside those paths, so they still use the shared sample cache. Found by checking the first deployment, shipped as 3.0.4. The same check showed that the worker's network-first path never stored anything: it cloned the response after handing it back, when the body can no longer be cloned, so only the files listed at install were available offline. The copy is now taken first, which is also what makes the test for this exclusion able to fail.

**Samples are shared.** `banks/` is about 40 MB of the 42 MB site and a Pages site is limited to 1 GB. When a pull request's `banks` tree hash equals main's, its preview is exported without `banks/` and the inline script redirects requests under `<preview>/banks/` to the live `banks/` by wrapping `fetch`. A preview is then about 1 MB. A pull request that changes samples gets its own copy.

**Purpose summary.** `summarize()` prefers the text under a heading named what, why, summary, purpose, overview, description or motivation, else the first paragraphs; it drops HTML comments, images and the generated-by line, keeps up to six bullets with a count of the rest, and clips at about 640 characters. Only `**bold**`, `` `code` `` and http(s) links are rendered.

**Failure is per pull request.** A ref that cannot be fetched, a tree with no `index.html` or no `<head>`: that pull request is listed with the reason and no preview; main and the others still deploy.

**Tests.** `test/pages.test.mjs` unit-tests the summary, escaping and listing, then builds a real site from the working tree (`git stash create` gives a commit of the tracked changes without touching the index or the stash list) with a same-repository pull request, a fork and a broken ref, serves it and drives the listing, the preview and the live app in a browser.
